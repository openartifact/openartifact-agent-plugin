# Explain a publish failure

Reference of the `explain-install-failure` skill for a failed publish or upload (`npm publish`, `twine upload`, `uv publish`, `cargo publish`, `gem push`, `dotnet nuget push`, `mvn deploy`, `helm push`, `swift package-registry publish`, `dart pub publish`, `curl -T`, a CI publish job).

1. **Read the error:** the HTTP status, the URL it was sent to (the repository is the `/repos/<name>` or `/repos/<format>/<name>` part), the package and the version. Quote the server's message; it often names the cause.
2. **Look at the repository** with `get_repository(name)` for the repository in that URL: `repo_type`, and for a group `deploy_target` and `members`, and `immutable_releases`.
3. **Explain the status:**
   - `401`: the client sent no token, or one the server does not accept, for that URL. Clients look tokens up by URL: npm by host and path, pub by the exact URL, SwiftPM only over `https`. Point at the credential setup of the `configure-project` skill, never at the token value.
   - `403`: the token may not write there. When the URL is a group with a `deploy_target`, write is checked on the hosted repository that `deploy_target` names, not on the group: a token or permission scoped to the group does not let it publish. A scoped token gets only what both its scopes and its owner allow. If `check_availability` for any version in that repository reports `repository_blocked`, the repository is blocked and no permission helps. You cannot see the publishing token's permissions: say which repository needs `write` for it, and that an administrator grants it.
   - `405`: the URL is read-only. A proxy never takes a publish; a group takes one only when `get_repository` shows a `deploy_target` (OpenArtifact 0.26.0 and later, and never for docker, deb, rpm, apk, pacman, swift, pub or cran groups). Name the hosted repository to publish to instead: the `deploy_target`'s member, or a `members` entry with `repo_type: hosted` (ask which one if there are several and nothing decides). Deleting, unpublishing or yanking through a group always answers `405`, even with a `deploy_target`: send it to the hosted repository. Do not suggest changing the group; an administrator can set a deploy target.
   - `409`: the version is already there, and a version is published once. `get_package(repository, name)` on the hosted repository shows whether it is listed and when it was stored. The way forward is a new version. With `immutable_releases`, a release cannot be overwritten or deleted either, except by an administrator (`?force=true`); replacing a published version is a team decision, since others may have installed it, so do not offer to delete it.
   - `413`: the file is above the format's size limit. Quote the message.
   - `422` with `LICENSE_METADATA_UNREADABLE`: the repository has a blocking license policy, and the server cannot read the license of this file (a damaged archive, a wheel without `METADATA`, a `.pom` that does not parse). Add the license to the package metadata in the form the format's tools write, and publish again.
   - `507` with `quota_exceeded`: the repository or its project is over its storage quota. Items in the trash count until they are purged. An administrator frees space, empties the trash or raises the quota.
   - `400`: the upload failed validation (name, version or checksum do not match, a required file is missing). Quote the message and compare it with the package's metadata.
4. **Through a group,** the answer comes from the hosted repository that stores the publish, so its message names that repository, not the group. Say so, so the user looks for the cause there.
5. **When the publish worked but the version then does not install,** a scan or license policy may have quarantined it after the upload: continue with the install steps of the skill (`check_availability` shows `quarantine` or `license_policy`).

Never suggest publishing somewhere else to get around the refusal: not to the public registry (that would publish the team's package to the world), not to another team's repository, not with someone else's token. The fix is the right repository, a new version, the license metadata, or a request to a registry administrator.
